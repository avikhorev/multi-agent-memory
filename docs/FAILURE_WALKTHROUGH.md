# Разбор провала: источник не прочитан (C6)

В [успешном примере C1](WALKTHROUGH.md) видно, как обновление превращается в ответ. Здесь — обратный случай из **сохранённого основного прогона**: агент не запросил предложенный источник, нужное событие не было записано, а ответ провалил проверку. Новых вызовов модели не требуется.

**Сценарий:** [`C6-eval-0002`](../data/eval/C6-eval-0002.json), 30 сессий. **Система:** исходная `ours`, повторы `r0` и `r1`. Вопросы возникают в сессиях 28–30, но некоторые ответы зависят от гораздо более ранних событий.

## 1. Какие данные были доступны

| Проверка | Ожидаемый ответ | Где он находился | Когда задаётся вопрос |
|---|---|---|---|
| `cp-1`, Planner | `2026-05-07` — начало UAT для `notifications` | `e-0002`, документ `D-011`, предложен Worker в сессии **1** | Сессия **28** |
| `cp-2`, Worker | `Tomas Iyer` — владелец `archive` | `e-0004`, источник из ранней сессии | Сессия **29** |
| `cp-3`, Reviewer | `343000` — бюджет `archive` | `e-0086`, ответ `read_status` в сессии **27** | Сессия **30** |

`e-0002` и `e-0086` — ответы инструментов (`tool_data`), `e-0004` — сообщение пользователя в сессии 2, оно записывается в память без действий Worker. **Предложенный источник не равен прочитанному:** раннер передаёт Worker описание доступного инструмента, а запись `Entry` появляется только после соответствующего `read_document` или `read_status` ([`live.py`](../src/mam/live.py), [`Simulator`](../src/mam/simulate.py)). Контрольная точка указывает нужный источник в `required_events`.

## 2. Что произошло в `ours`

На первом вызове Worker в сессии 1 выбрал `update_record`, а не `read_document(D-011)`; в сессии 27 он снова выбрал `update_record` вместо `read_status(Atlas/archive)`. Это видно в [`r0` трассе](../results/live/main/traces/ours__C6-eval-0002__r0.jsonl) и [`r1` трассе](../results/live/main/traces/ours__C6-eval-0002__r1.jsonl).

| Проверка | `ours`, r0 | `ours`, r1 |
|---|---|---|
| `cp-1`: начало UAT | Не пройдена; `agent`, контекст неверен | Не пройдена; `agent`, контекст неверен |
| `cp-2`: владелец | Пройдена; `ok` | Пройдена; `ok` |
| `cp-3`: бюджет | Не пройдена; `agent`, контекст неверен | Не пройдена; `agent`, контекст неверен |

Оба повтора не содержат операции `write` для `e-0002` и `e-0086`, но содержат запись `e-0004`. Поэтому `cp-2` проходит, а на `cp-1` Planner говорит, что специфическая дата для `notifications` отсутствует; на `cp-3` Reviewer не находит бюджет `archive`. Само хранение пропущенного документа здесь проверить невозможно: **документ не поступил в память**.

## 3. Как присвоена метка `agent`

На обеих непройденных проверках `reachable = true`: исходное событие было доступно в сценарии. Однако `written_event_ids` не содержит ни одного события из `required_events` соответствующей точки. Функция [`label_failure`](../src/mam/scoring.py) сначала проверяет `refusal` и успешность действия, затем отсутствие записи требуемого события — и **до проверки качества контекста** возвращает `agent`.

Таким образом, `agent` — **метка согласно алгоритму**, а не установленная психологическая причина выбора инструмента. `context_passed = false` здесь тоже верно: нужного значения в памяти нет. Но это не доказывает, что реализация `ours` неправильно сохранила уже полученный факт.

Для контраста, [`full_history`, r0](../results/live/main/units/full_history__C6-eval-0002__r0.json) и [`r1`](../results/live/main/units/full_history__C6-eval-0002__r1.json) прочитали оба источника: `cp-1` и `cp-3` прошли. При этом `full_history` в `r0` **не прошла** другую проверку — `cp-2` (`model`, неверный ответ при верном контексте). Один удачный проход источника не означает лучшего поведения на всех вопросах.

## 4. Проверить по сохранённым данным

Из корня репозитория, Python 3.11+, без LLM и без изменения файлов:

```bash
python3 - <<'PY'
import json
from pathlib import Path

scenario = "C6-eval-0002"
for system in ("ours", "full_history"):
    for repeat in (0, 1):
        name = f"{system}__{scenario}__r{repeat}"
        unit = json.loads((Path("results/live/main/units") / f"{name}.json").read_text())
        trace = [json.loads(line) for line in
                 (Path("results/live/main/traces") / f"{name}.jsonl").read_text().splitlines()]
        written = {row.get("entry_id") for row in trace if row.get("op") == "write"}
        outcomes = {row["checkpoint"]: row["label"] for row in unit["checkpoints"]}
        print(system, repeat,
              "read D-011:", "e-0002" in written,
              "read STATUS:", "e-0086" in written,
              "labels:", outcomes)
PY
```

Ожидаемые признаки: у обоих `ours` — `False`, `False` и `agent` для `cp-1`, `cp-3`; у обоих `full_history` — `True`, `True` и `ok` для этих двух точек. Если нужен точный текст ответа, смотрите `checkpoints[].answer` и `violations` в тех же файлах `units/`.

## 5. Как интерпретировать

Этот кейс объясняет часть результата C6: `ours` получила **12/18** выбранных живых проверок против **15/18** у `full_history` ([E4](EVIDENCE.md#e4), [раздел 8 отчёта](../REPORT.md#8-разбор-провалов)). Он показывает цепочку «инструмент не вызван → источник не записан → контекст неполон → ответ неверен» при данном протоколе из четырёх вызовов модели за сессию. Он **не** изолирует причину выбора инструмента и не устанавливает, как системы повели бы себя при принудительном чтении или более длинном цикле агента.

Сопоставление меток `agent`, `memory`, `model` и ограничений классификации — в [правилах оценки](SCENARIO_FORMAT.md#метки-провала) и [реестре проблем](KNOWN_ISSUES.md#agent-protocol).
