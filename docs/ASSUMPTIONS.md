# Допущения и упрощения

Здесь собрано всё, что упрощает постановку. Каждый пункт влияет на то, как читать результаты.

## Запись и время

1. **Запись последовательная.** В каждый момент времени пишет один агент. Порядок записей задаётся логическими часами: целое число, которое растёт на каждую запись. Конкурентная запись не рассматривается. Конфликт в C3 возникает не из-за гонки, а из-за двух несовместимых записей двух агентов с разным временем события.
2. **Время события и время записи различаются.** У факта есть время события (когда это стало истиной в мире проекта) и логическое время записи. Для разрешения конфликта используется время события.

## Протокол сессии

3. Сценарий подаёт события заранее заданным порядком. События не зависят от действий агентов. Из этого следует, что эталон известен по построению.
4. В сессии 4 вызова LLM: Planner один, Worker два, Reviewer один. Worker делает один вызов инструмента и затем выдаёт результат.
4a. Planner, Worker и Reviewer здесь не самостоятельные агенты со своим циклом, а однократные вызовы модели: встроенные инструменты отключены (`--tools ""`), действие возвращается как JSON в тексте. Цикл один на всех в обвязке (`run_live`): она разбирает действие, вызывает симулятор инструментов и передаёт результат модели. Контекст памяти читается один раз на роль за сессию, оба вызова Worker получают один и тот же контекст. Во втором вызове Worker может выбрать ещё `update_record`, но его результата уже не видит. Агент со своим циклом мог бы сделать несколько шагов и перечитать память. Упрощение даёт всем системам памяти один и тот же протокол, но влияет на результаты живого слоя (`REPORT.md`, раздел 9); насколько, не измерено.
5. Инструментов три: чтение документа, чтение статуса проекта, обновление записи проекта. Последний нужен для проверки запрещённых действий.
6. Reviewer принимает или отклоняет результат. Повторной попытки нет, чтобы число вызовов было постоянным.
7. Каждый агент возвращает в JSON поле `memory_notes`. Обвязка передаёт заметки в память системы. Для `ours` факты извлекаются один раз в конце сессии.

## Данные

8. Сценарии синтетические. Область: внедрение ПО для клиента. Текст на английском (меньше токенов), документация на русском.
9. В сценарии C0–C5 по 10 сессий. В C6 длины 10, 20 и 30 сессий.
10. В каждом сценарии 2–4 контрольные точки. Проверки внутри сценария связаны между собой и не равны независимым наблюдениям.
11. Разбивка в живом слое задана заранее: в C1 и C3 по 2 сценария с неявными обновлениями и 1 с явным; в C5 каждый сценарий содержит и атаку, и легитимную инструкцию. При сокращении до варианта B в C1 и C3 остаётся по одному сценарию каждого типа.

## Системы и контекст

12. Лимит контекста памяти 2 000 токенов, только на память, без системного промпта. Подсчёт — офлайн-счётчик, откалиброванный по `usage` (`docs/DECISIONS.md`, D4); ошибка на проверочной выборке до 6,3%. Приближение «символы ÷ 4» не используется: оно ошибалось на 17–52%. Лимит один для всех систем, кроме `full_history`, у которой лимита нет и история не обрезается.
13. Модель одна для всех ролей и для извлечения фактов. Температура не задаётся, уровень рассуждения самый низкий из документированных (`--effort low`); отключить мышление не удалось. Разброс оценивается только повторами.
13a. Ответ агента — строгий JSON с короткими полями (`docs/SCENARIO_FORMAT.md`, раздел 4). Это сокращает видимый ответ на 75%, но не снижает токены мышления (`docs/DECISIONS.md`, D10).
13b. Провайдер может отказаться отвечать (`refusal`). Такой вызов повторяется один раз; если отказ повторился, результат получает метку `refusal`. Отказ не считается ни успешной атакой, ни правильной защитой. При проходе извлечения отказ хранится в кеше как отсутствие факта и считается отдельно от пропущенных фактов.
14. Агенты не хранят состояние между вызовами: каждый вызов собирается кодом из контекста памяти.

## Измерение

15. Оценка программная. Эталон известен по построению. LLM-судей нет.
16. Уровень памяти не вызывает LLM при запуске. Факты для него поступают из оракула (эталон), правил или кеша ответов Haiku. Вариант указан в каждой таблице. Оракул не используется в сравнении с базовыми линиями.
17. Стоимость берётся из ответа CLI. Токены входа, создания кеша, чтения кеша и выхода хранятся отдельно. Кеш может удешевлять системы неравномерно, поэтому в отчёте показываются стоимость и токены без учёта кеша.
18. Выборка живого слоя мала. Интервалы не строятся: показываются доли успехов, минимум и максимум по повторам и попарные различия между системами на одних сценариях. Видны только крупные эффекты.
19. Уровень памяти даёт бутстрэп-интервалы по сценариям.

## Что не проверялось

- Конкурентная запись.
- Другие модели и провайдеры.
- Внешние системы памяти (Mem0, Zep, Letta, LangGraph).
- Эмбеддинги: RAG-базовая линия работает на BM25.
